# Open-Meteo data for the BYD widget

The [implementation note](widget-mapping-implementation.md) records which researched fields are now converted in the updated 1.1.1 build.

Research date: 2026-10-01. Application baseline: `478a255ce9b12b5169d9fd65a122b75b2c76d5f3`, the published BigDataCloud 1.1.1 source. Official Open-Meteo server source is pinned to `b06f4760fd1f997e5559bb380f64c5e496b4a509`. The complete public adapter attribute inventory and limits of native-parser evidence are recorded separately in [byd-widget-schema.md](byd-widget-schema.md). This note defines which upstream values can fill those attributes and which conversions remain unsupported. [1], [2]

## Findings that affect implementation

The baseline already requests apparent temperature, humidity, pressure, visibility, UV, sustained wind, gusts, cloud cover, precipitation, and day/night for current conditions. Its largest data gaps are not additional current-temperature variables: they are the eight-hour request cap, identical daily day/night objects, omitted native daily fields, and the limited air-quality request. District and city names are outside the forecast API and must come from the geocoder. [1], [2], [3]

Open-Meteo accepts hourly variables as current variables through the same variable loader. Current `visibility` and `uv_index` are supported in the examined source; they are not invalid query names. Model availability can still yield JSON `null`. The baseline treats several such values as mandatory and rejects the entire update when they are absent. Any newly added optional field should omit unavailable data instead of changing a missing forecast into a measured zero or rejecting otherwise usable weather. [1], [3], [4], [5]

### Request horizon and selecting widget hours

The baseline has `past_days=1&forecast_days=15&forecast_hours=8`. The server independently evaluates the hourly range when `forecast_hours` is specified, starting at the current hour by default. Consequently, those eight points cannot describe sixteen dates of separate day and night conditions. Removing `forecast_hours` and leaving `past_days=1&forecast_days=15` causes hourly data to fall back to the daily range, at one-hour resolution. This covers yesterday plus fifteen forecast dates, nominally 384 samples. The production probe described below confirmed 384 hourly timestamps and sixteen daily dates. [1], [6], [12]

After widening the request, the widget's eight visible hourly points must be selected from the current forecast hour forward, rather than taking array indices 0–7, which would now be yesterday's first hours. Use the response time zone for both the cutoff and day grouping. Eight displayed points and full hourly input coverage serve different purposes; widening input need not change the widget's visible hourly count. [1], [2], [6]

Open-Meteo defaults to Celsius, km/h, millimetres, and ISO 8601 times. Pin these query units explicitly when the converter assumes them. `timezone=auto` resolves an IANA zone and returns its name and `utc_offset_seconds`; ISO timestamps are formatted in that response zone. Parse them in the response zone rather than the Android device zone. Unix timestamps, if selected instead, are epoch seconds and require multiplication by 1000 for native epoch-millisecond fields. Do not apply a second UTC offset to an already parsed epoch instant. [3], [5], [6], [7]

### Directly usable and convertible weather data

The target attributes below are evidenced by the public adapters, not a universal BYD SDK. The casing and JSON number/string distinction must match [byd-widget-schema.md](byd-widget-schema.md). Do not assume that every stock launcher renders every field. [2]

| Widget attribute or purpose | Exact Open-Meteo input | Conversion and limitation |
| --- | --- | --- |
| Current `temperature`, `realfeel` | `current.temperature_2m`, `apparent_temperature` | Rounded Celsius, already mapped. Apparent temperature is a legitimate feels-like value; it does not establish an independently defined shade temperature for `feelTemperatureShade`. [1], [2], [3] |
| Current `humidity`, `pressure`, `visibility` | `relative_humidity_2m`, `pressure_msl`, `visibility` | Relative humidity %, mean-sea-level pressure hPa, and metres converted to kilometres. Use a deliberate rounding policy; rounding metres followed by integer division truncates kilometres. [1], [2], [8] |
| Current `uVIndex`; daily `uvIndex`, `uvIndexText` | `current.uv_index`, `daily.uv_index_max` | UV is dimensionless. Numeric UV can be emitted directly or rounded to the native numeric convention; `uvIndexText` can contain the actual formatted numeric value. A native descriptive vocabulary for `uvIndexDesc` is unverified. [2], [3], [9] |
| Current `windspeed`, `windgustspeed`; gust-level fields | `wind_speed_10m`, `wind_gusts_10m` | Speeds in pinned km/h. A sustained-wind level and gust level must each derive from their own speed. The baseline's linear five-km/h buckets are not a documented Beaufort conversion; native scale and the exact standard conversion must be established before replacing it. Open-Meteo does not provide a separate gust-direction field. [1], [2], [3], [8] |
| Hourly `precipitation` | `hourly.precipitation` | Number in mm for the corresponding upstream interval. Baseline omits this native adapter attribute. Preserve decimals and do not describe it as a whole-day total. [1], [2], [3], [8] |
| Hourly `rainprobability`; half-day `precProb` | `hourly.precipitation_probability` | Percentage probability of precipitation, not a separate probability of rain alone. A native `rainProb` string can only be a documented compatibility alias for this broader probability. Do not relabel it as independently measured rain-only probability. [1], [2], [3] |
| Daily `realFeelTempMin`, `realFeelTempMax` | `daily.apparent_temperature_min`, `apparent_temperature_max` | Rounded Celsius represented as strings because those are the observed native adapter types. These are actual feels-like extrema and improve on an adapter copying ordinary temperature extrema. [2], [9] |
| Daily `pressure`, `visibility` | `daily.pressure_msl_mean`, `visibility_min` (or explicitly chosen `visibility_mean`) | hPa and metres-to-kilometres. Minimum visibility represents the worst daily visibility; mean and minimum are different summaries, so record the chosen policy. Both exact variable names are in the official daily enum. [2], [9] |
| Daily day/night weather IDs and `weathertext` | Full-horizon `hourly.weather_code`, `is_day` | Group by local calendar date, partition using `is_day`, and aggregate each half separately. The server's whole-day `weather_code` is literally the maximum hourly WMO weather code; independently applying that same rule to each half is a clear derived policy. It must not copy the whole-day code to both halves. Missing halves need an explicit fallback policy, including polar daylight/night. [1], [2], [9], [10] |
| Day/night `humidity`, `cloudCover`, wind and gust fields | Full-horizon hourly `relative_humidity_2m`, `cloud_cover`, `wind_speed_10m`, `wind_direction_10m`, `wind_gusts_10m` | Representative-hour values or independently aggregated half-day values are both possible, but they are different policies. Use documented means/maxima where chosen. Direction aggregation must be circular/vector-based; arithmetic mean of 359° and 1° is wrong. Native `cloudCover` and `windGustPow` are strings in the examined daily-condition adapter. [2], [9], [10] |
| Day/night liquid precipitation attributes | `hourly.rain`, `showers`, `precipitation`; daily `rain_sum`, `showers_sum`, `precipitation_sum` | `rain + showers` is liquid rainfall in mm; total `precipitation` also includes snow water equivalent. Native `rain` and `totalLiquid` should not both blindly receive total precipitation. Daily sums are whole-day quantities and cannot be inserted as separate half-day totals. Native period semantics remain unverified, so define the selected-hour or half-day aggregation policy. [2], [3], [8], [9] |
| Snow amount opportunities | `hourly.snowfall`, `snowfall_water_equivalent`; daily `snowfall_sum`, `snowfall_water_equivalent_sum` | Default snowfall depth is cm; snow water equivalent is mm. These are different measurements, not interchangeable values. Native daily-condition `snow` units are unknown, so an amount cannot safely be inserted until that contract is established. Actual snowfall does not imply a measured `snowProb`. [2], [4], [9] |
| Daily maximum gust and additional precipitation summaries | `wind_gusts_10m_max`, `precipitation_probability_max`, `precipitation_hours`, `rain_sum`, `showers_sum`, `snowfall_sum`, `precipitation_sum` | Available source features, but request only values with a verified target and purpose. A probability maximum, wet-hour count, precipitation amount, and gust speed describe distinct things. The source also offers apparent-temperature and pressure mean/max/min variants. [9], [10] |

Hourly precipitation and snow-water input use backward interval sums in the official model definitions. An amount at timestamp T concerns the preceding interval, whereas `is_day` represents daylight at T. When deriving half-day amounts, specify how an interval crossing sunrise, sunset, or midnight is assigned; grouping solely by the ending timestamp is an approximation and must not silently claim exact astronomical partitioning. A selected-hour adapter should retain the source interval meaning. [8], [10]

### Real lunar events are available

The current official server has daily variables `moonrise`, `moonset`, and `moon_phase`. The former two are timestamp columns, with `daily_units.moonrise/moonset` matching the selected time format. In default ISO mode they are date-time strings in the response zone; in Unix mode they are epoch seconds. They can map to native `moonRise`, `moonSet` epoch milliseconds and matching formatted strings. This supersedes any older blanket statement that Open-Meteo offers no lunar variables. Production availability was confirmed by an HTTP 200 probe on 2026-10-01. [3], [5], [7], [9], [11], [12]

The source computes events for the local calendar day. If the moon does not rise or set during that day, the event is `Timestamp.noData`, serialized as JSON `null`, not midnight. Treat this as an optional missing event. The public Denza investigation reports that stock min/max date selection depends on `moonSetFmt`; therefore a date-preserving compatibility fallback for that formatted field may still be required when no actual event exists. Keep the compatibility date distinguishable from a fabricated moonset instant. [2], [5], [7], [11]

`moon_phase` is a floating fraction in `[0,1)` evaluated at local noon: 0 means new moon, 0.25 first quarter, 0.5 full moon, and 0.75 last quarter. Its unit is `fraction`. This is a cycle fraction, not illuminated-disc percentage. The native adapter's `moonphase` is a string with no verified vocabulary; direct conversion to a guessed name or enum is unjustified until native parsing is known. [2], [3], [11]

### Air quality and pollutant gases

The baseline requests current `european_aqi`, `pm10`, and `pm2_5`, emits current AQI and particulate concentrations, and uses European category boundaries 20/40/60/80/100. That existing classification is consistent with the selected scale. It must not be described as a current scale-conversion defect. [1], [13]

Open-Meteo also provides current and hourly `ozone`, `carbon_monoxide`, `nitrogen_dioxide`, and `sulphur_dioxide`. All four upstream concentrations are in μg/m³, as are `pm10` and `pm2_5`. The public native adapter names corresponding fields `o3`, `co`, `no2`, and `so2`, but only writes zero placeholders and does not establish their native concentration units. In particular, CO must be divided by 1000 only if the target is verified to use mg/m³. Do not assume a unit from the short field name or blindly round all gases to integers. [2], [14], [15]

European and U.S. AQI are different defined indices. The official source exposes `european_aqi` and `us_aqi` and pollutant subindices, but not a native Chinese AQI variable. Requesting `us_aqi` legitimately changes to that documented scale; it does not convert European AQI into Chinese AQI. A Chinese index requires the applicable standard's concentration breakpoints, averaging periods, pollutant selection and rounding rules, not a multiplier or a relabelled U.S. value. [13], [14]

Hourly AQI and PM2.5 can enrich daily numeric summaries if the application's policy explicitly defines them, for example a day's peak hourly European AQI. That is a derived peak summary, not an official daily air-quality index. The native `aqidays` array's item schema is unknown and neither public adapter populates it, so it cannot safely be filled by guessing objects. The Air Quality API schema permits up to seven forecast dates, default five; underlying CAMS global source has 121 forecast hours and European source 97, so requested range is not a guarantee of finite values for every day. Do not fill all sixteen weather dates by repeating the current AQI. [1], [2], [14], [15]

### Attributes without a verified equivalent

No examined documented forecast or air-quality schema supplies official warning objects matching native `alarm`, native `liveInfos` lifestyle objects, city/district names, country/admin names, traffic restrictions, festival names, or a native radar-animation URL. A WMO thunderstorm code, snowfall amount, or high wind does not establish an official warning or a measured thunder/snow/ice probability. `pressureTendency`, shade feels-like temperature, native lunar phase vocabulary, pollutants' native units, and `aqidays` items remain contract questions. Leave those unsupported fields absent or empty according to the known adapter shape; do not fabricate values simply to make a larger payload. [2], [3], [4], [14]

Metadata such as `expiretime`, source attribution, update timestamps and links can be populated by adapter policy using the existing shape, without inventing a meteorological measurement. Keep successful-refresh time separate from forecast-observation time; the native-adapter investigation found that these timestamps affect the displayed release-time label. [1], [2]

## Live production checks

The parent task performed two unauthenticated Open-Meteo checks on 2026-10-01 using public Amman reference coordinates 31.9566, 35.9457, not the user's private GPS fix. Both returned HTTP 200. The retained JSON fixtures are workspace research evidence rather than files containing credentials. [12]

- `/workspace/scratch/byd-build/openmeteo-lunar-probe.json`: `daily=moonrise,moonset,moon_phase,apparent_temperature_max,apparent_temperature_min,wind_gusts_10m_max,pressure_msl_mean&timezone=auto&past_days=1&forecast_days=1`. Response zone was `Asia/Amman` with UTC offset 10800, and lunar units were `iso8601` and `fraction`. September 30/October 1 rise times were 20:37/21:31, set times 10:23/11:34, with cycle fractions approximately 0.633/0.670. [12]
- `/workspace/scratch/byd-build/openmeteo-expanded-probe.json`: current weather variables plus full hourly precipitation/rain/showers/humidity/cloud/gusts, and daily apparent-temperature extrema, mean sea-level pressure, minimum visibility and lunar events. With `past_days=1&forecast_days=15` and no `forecast_hours` cap, response contained 384 hourly points and sixteen daily dates in `Asia/Amman`, with Celsius/km/h/mm units. This establishes production support for the examined query at this public reference location; optional model availability elsewhere still needs null handling. [12]

No native-car rendering result is claimed by these network probes. Native exact parsing and target-unit limits remain those in the companion schema investigation. [2]
